## Goal

Add a read-only `/admin/ops` operational summary page behind the existing
Cloudflare Access admin boundary.

This is the first "operational audit information" step. Keep it deliberately
small: show aggregate counts that help an operator understand current D1 state,
without exposing user identities, album titles, password/session data, tokens,
PhotoPrism identifiers, R2 object keys, or any row-level inventory beyond what
existing admin inventory pages already expose.

Claude Code may delegate implementation and tests to a Sonnet subagent, but the
primary coordinator must review the final diff against the security constraints
below before reporting.

## Background

Current admin routes already include:

- `GET /admin`
- `GET /admin/users`
- `GET /admin/albums`
- `GET /admin/permissions`
- several admin POST mutations for users, albums, and permissions

The project roadmap still lists:

- sync request/status administration
- operational audit information without sensitive-data leakage
- later cleanup/R2 work

This handoff implements only a read-only operational D1 summary. It does not
start sync jobs, read Docker state, inspect R2, or create an audit-log system.

Existing patterns to follow:

- `workers/src/routes/admin.tsx` for route wiring, SSR pages, sanitized errors,
  `no-store`, and `AdminRouteDeps`.
- `workers/src/services/admin-*-repository.ts` for D1 repository style and
  row validation.
- `workers/test/admin-routes.test.ts` and existing admin repository tests for
  test shape.
- `workers/README.md` admin surface tables for documentation style.

## Acceptance Criteria

### Route and UI

- Add `GET /admin/ops`.
- It must be mounted under the existing `admin.use('*', guard)` and before the
  catch-all `admin.all('*', ...)`.
- `GET /admin` must link to `/admin/ops` with Japanese label `運用サマリ`.
- `GET /admin/ops` returns:
  - `200` for verified and allowlisted admins;
  - `403` for auth failures via the existing guard;
  - `500` with sanitized fixed text for repository/D1 failures;
  - `Cache-Control: no-store` on all admin responses, consistent with existing
    admin pages.
- The page must be server-rendered with existing `Layout`; no client-side JS.
- The page must display only aggregate counts, not row-level data.

### Summary Content

Create an `AdminOpsSummary` type with these sections and fields:

```ts
export interface AdminOpsSummary {
  generatedAt: string
  users: {
    total: number
    enabled: number
    disabled: number
    locked: number
  }
  albums: {
    total: number
    enabled: number
    disabled: number
    expired: number
    expiringSoon: number
    downloadable: number
  }
  permissions: {
    total: number
  }
  sessions: {
    total: number
    expired: number
  }
}
```

Use a single `now` timestamp generated by the route from `deps.clock()`.
Pass `now.toISOString()` to the repository. `generatedAt` must be that same
canonical timestamp.

Define "expiring soon" as an album with `expires_at IS NOT NULL`,
`expires_at > now`, and `expires_at <= now + 7 days`. Compute the plus-7-days
timestamp in the route or repository, but validate it as canonical UTC before
using it in D1.

Define "locked users" as `locked_until IS NOT NULL AND locked_until > now`.
Define expired sessions as `expires_at <= now`.
Define expired albums as `expires_at IS NOT NULL AND expires_at <= now`.

### Repository

Add a new repository, for example:

- `workers/src/types/admin-ops.ts`
- `workers/src/services/admin-ops-repository.ts`

Repository method:

```ts
getSummary(now: string, expiringSoonUntil: string): Promise<AdminOpsSummary>
```

Use parameterized SQL. Suggested approach: one repository method issuing four
aggregate queries:

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN enabled = 1 THEN 1 ELSE 0 END) AS enabled,
  SUM(CASE WHEN enabled = 0 THEN 1 ELSE 0 END) AS disabled,
  SUM(CASE WHEN locked_until IS NOT NULL AND locked_until > ? THEN 1 ELSE 0 END) AS locked
FROM users
```

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN enabled = 1 THEN 1 ELSE 0 END) AS enabled,
  SUM(CASE WHEN enabled = 0 THEN 1 ELSE 0 END) AS disabled,
  SUM(CASE WHEN expires_at IS NOT NULL AND expires_at <= ? THEN 1 ELSE 0 END) AS expired,
  SUM(CASE WHEN expires_at IS NOT NULL AND expires_at > ? AND expires_at <= ? THEN 1 ELSE 0 END) AS expiring_soon,
  SUM(CASE WHEN download_enabled = 1 THEN 1 ELSE 0 END) AS downloadable
FROM albums
```

```sql
SELECT COUNT(*) AS total
FROM album_permissions
```

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN expires_at <= ? THEN 1 ELSE 0 END) AS expired
FROM sessions
```

Do not use `SELECT *`.
Do not join to `users` or `albums`.
Do not select IDs, display names, titles, hashes, token hashes, PhotoPrism UIDs,
transform settings, object keys, or other row-level data.

Validate repository inputs before D1:

- `now` and `expiringSoonUntil` must both be canonical UTC timestamps.
- `expiringSoonUntil` must be strictly greater than `now`.

Validate every aggregate row after D1:

- row must be a non-null object;
- expected keys must be present;
- every value must be a safe non-negative integer;
- reject `null`, `undefined`, negative, non-integer, string, `NaN`, and
  unexpected shapes by throwing `databaseOperationError()`.

On any D1 prepare/bind/first failure, missing row, malformed row, or invalid
aggregate value, throw the existing sanitized `databaseOperationError()`.

## Constraints

- Preserve all existing auth and admin guard behavior.
- `GET /admin/ops` must be read-only.
- No POST, forms, buttons, or mutations in this handoff.
- No R2 reads/writes/lists.
- No PhotoPrism, NAS, Docker, Portainer, GitHub, or Cloudflare API calls.
- No new dependencies.
- No migrations.
- No secrets or real config values.
- No logging of admin identity, D1 errors, counts, timestamps, request headers,
  or environment values.
- Do not expose:
  - `password_hash`
  - session `token_hash`
  - Access JWT claims or admin email
  - `display_name`
  - album `title`
  - `photoprism_album_uid`
  - transform settings (`thumb_*`, `preview_*`, `strip_exif`)
  - R2 object keys or manifest/photo data
- Do not weaken existing Content-Type, Origin, auth, or mutation validation
  helpers.
- Keep the implementation consistent with existing admin route and repository
  patterns. Avoid broad refactors.
